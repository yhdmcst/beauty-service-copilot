# 技术架构

版本：`compact-v10-service-continuity-3`。

## 应用结构

Flask提供页面和API，Socket.IO推送分析与任务更新。模型通过Ollama兼容接口调用本地 `qwen3:8b`。SQLite保存分析、回复审核、人工任务及操作历史。

```text
聊天、订单、工单
       |
会话关联与分析时点
       |
LangGraph工作流
       |
建议、证据、风险任务
       |
客服审核与跟进
```

## 数据处理

`src/data/contest_data.py`读取三类业务记录。“附件快照”展示提供的附件状态；“历史回放”按选定买家消息截断，排除后续聊天及工单，无法还原的历史状态显示未知。

昵称相似只提供关联候选，客服确认身份并填写依据后才合并跨会话服务轨迹。新增输入独立保存，仅在同一会话、同一分析点复用；历史回放不读取新增轮次。

## 分析流程

| 节点 | 处理 |
| --- | --- |
| evidence | 读取当前问题及关联记录，确定可用证据 |
| safety | 识别诉求、情绪和风险，先登记风险任务 |
| draft | 检索资料，生成回复与下一步，核对业务声明 |
| verify | 补充来源、时点提示和人工复核任务 |
| audit | 保存分析、调整记录、节点耗时和Token用量 |

编排实现见 `src/orchestration/workbench_workflow.py`，建议生成见 `src/agents/assist_agent.py`。各节点设计见 [Agent设计](AGENT_DESIGN.md)。

## 回复与风险

明确诉求先由规则定位，模糊意图可由同次模型生成补判。基础情绪、业务场景和风险分开记录，模型不能降低规则确定的风险下限。

事项状态记录买家当前、暂缓、条件、取消和自述已解决的变化。只有一个未解决事项时，系统才承接“进度怎么样”等简短追问；多订单或多事项对应不明时交由客服确认。

已有资料显示来源、时间和原话。消费者说“发过照片”与附件是否实际收到分别记录。回复计划区分客服内部核查和必要追问，减少重复索取信息。

默认知识检索采用词法方法，只有通过本次支持检查的资料正文进入生成。JSON Schema、Pydantic和业务规则检查输出结构、金额、状态、来源及执行承诺；原稿、修正和原因一起保存。

## 性能与存储

紧凑输出字段、360 Token单次输出上限、精确缓存和有界队列控制开销。缓存按提示版本、提供方及模型配置隔离，命中后仍执行当前风险检查。

明确问候及符合条件的单订单既往发货查询可直接使用证据。风险、混合诉求或有争议的历史继续完整分析。

默认检索、向量存储和缓存均在本地进程中运行，无需额外服务。数据库由当前机器首次运行时创建。工作台不接真实退款、补发、改址或客户消息发送接口。
