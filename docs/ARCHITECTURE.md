# 技术方案

版本：`compact-v9-item-issues-2`。节点、状态和异常处理详见 [Agent设计](AGENT_DESIGN.md)。

## 应用

Flask负责页面和API，Socket.IO推送更新。本地Qwen3:8b通过Ollama兼容接口生成JSON建议，SQLite保存分析、审核和人工任务。数据使用赛题虚构聊天、结构化订单及工单，默认词法检索和进程内缓存。

## 工作流

| 节点 | 作用 |
| --- | --- |
| Evidence | 按会话和买家消息确定时点，关联本会话或已确认身份的记录；历史回放排除未来信息 |
| Safety | 识别并先保存风险任务，模型排队不会推迟登记 |
| Draft | 证据/知识检查、限用证据路径或模型生成，以及文本声明校验 |
| Verify | 关联证据、时点警示和必要的人工复核任务 |
| Audit | 保存结果、原稿/修正、执行记录和实际用量 |

实现：`src/orchestration/workbench_workflow.py`及 `src/agents/assist_agent.py`。

人工编辑、采纳、拒绝和任务状态更新由应用单独保存。没有自动发送消息、改订单或执行商家售后，也未使用LangGraph的interrupt或持久化checkpoint。

## 智能分析与约束

明确诉求由轻量规则识别，模糊意图可由同次生成补判。基础情绪与场景标签分开，风险下限不能由模型降低。

当前意图和处理焦点共用明确拒绝请求识别，保留“没有赠品”“退款没到账”等真实缺失结果。分类视图只用于定位问题，原聊天和风险检查不改写。

商品问题使用共享线索，避免“快递、包裹”等词盖过少件或损坏。少件下一步核对购买/实收数量、装箱与分包，减少客服只追查物流的偏差。买家称照片已提供时，先查收到与可用情况，不无条件重复索取；自述上传不作文件存在证明。

沟通重点提取消费者已提供信息、等待结果和明确自述肤质，保留消息ID、时间及原话。未来/客服消息不当作当前消费者偏好，冲突不自动解决。礼貌致谢、第三方情绪及咨询型投诉表述与消费者实际情绪区分。实际不适仍由独立安全规则触发人工处理，不因语气平静降低风险。

JSON Schema和Pydantic约束输出结构，有限的业务规则核对金额、状态、来源、时点、执行承诺及未核实原因。原稿和修改保存，格式和规则检查通过后，仍需人工核对语义。

V8-4知识门禁逐条返回 `supported_document_ids`，生成器只读本次支持的资料正文。可插拔重排只调整候选顺序，不改资料、来源或审核状态；排名不能赋予业务授权。CPU词法重排和分类实验不默认启用。

V8-5已有资料列表按买家消息及订单字段构建，保留来源、时间、session与资料状态。未确认关联历史不读取，未来/客服/第三方材料不转成当前买家资料。自述上传与附件文件可用性分开，冲突不覆盖原历史，展示不增加单独模型调用。

## 性能成本

紧凑字段、360 Token输出上限、按版本/模型配置隔离的精确缓存和有界队列减少重复请求。仅无风险且明确的问候、单订单既往发货/运单查询可以走证据路径。

规则路径不代替混合问题、风险或历史争议的分析；相似咨询不一定具有相同订单事实，当前不使用语义缓存。

## 数据与身份

快照不能当成历史状态。历史回放排除未来记录，缺历史状态时明确未知。昵称只提供跨会话关联候选，人工填写依据后才合并轨迹。

上传包的字段清理、匿名昵称和公开授权边界见 `DATA_POLICY.md`。数据库在运行时生成，初始没有原开发环境的人工数据。
