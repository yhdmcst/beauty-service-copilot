# 项目报告

文件核对：2026-10-15。版本：`compact-v9-item-issues-2`。

## 作品解决什么问题

美妆客服接待时要在聊天、订单和售后工单之间切换。同一位消费者可能已经解释过退款经过、提供过照片，客服却还要重新询问。工作台把相关记录放在一起，给出带依据的回复草稿和待核事项，由客服审核并继续处理。

作品包含智能接待辅助和风险跟踪看板。它不向消费者自动发送消息，不执行退款、补发、改址，不作医疗诊断或商品真伪鉴定。使用的数据为赛题虚构业务材料。

## 已实现的功能

| 场景 | 实现 | 使用边界 |
| --- | --- | --- |
| 查清服务经过 | 聊天、订单、工单关联；快照与历史回放分别查看 | 回放排除未来记录，不能还原的状态标为未知 |
| 理解当前问题 | 当前诉求、商品问题及少件线索；模糊意图由同次生成补判 | 否定、假设和复杂多诉求仍可能有误 |
| 回应消费者顾虑 | 基础情绪、场景标签和原话来源；沿用已提供资料 | 上传自述不等于文件已收到，肤质自述不等于产品适配结论 |
| 生成可审核草稿 | 本地Qwen3:8b、结构校验、业务声明与服务行为检查 | 规则覆盖有限，客服仍需审核语义 |
| 跟进风险 | 先登记风险任务，支持认领、备注和状态历史 | 完成任务不等于完成商家退款 |
| 保存审核过程 | 草稿、修正、采纳/拒绝及修改分别留存 | 自动预审不能写成人工确认 |

Flask提供工作台，LangGraph执行 `evidence → safety → draft → verify → audit`，SQLite保存分析与操作。具体输入、节点及异常处理见 [Agent设计](AGENT_DESIGN.md)。

## 性能与成本

当前12例输入6783、输出1573，共8356 Token；系统中位2834.98毫秒、样本最大3685.6毫秒。与V8-5的8357 Token相比差1 Token，不作显著降本或单因素提速结论。没有增加独立分类模型调用。

已采用紧凑字段、360 Token单次输出上限、按版本及运行配置隔离的精确缓存，以及限于明确低风险请求的证据路径。缓存命中后仍执行本次风险检查。

历史对照单独报告：2026-10-09固定11个共同案例、两版各22次交替生成，总Token16368→15364，减少6.13%；2026-10-13固定同提示、CPU与5060各6次，中位17.18→3.82秒。离线预审分流的23.08%节约不计入接待成本。这些结果不包含硬件、电费、生产并发和人工效率。
